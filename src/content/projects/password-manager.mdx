A web app for passwords and files where the server stores everything and can read none of it. Encryption and decryption run in the browser. The server keeps a verifier for the master password, a vault key it cannot unwrap, and blobs it cannot open.

This is the second design. The first one stored the derived master key in the database next to the ciphertext it unlocked, which I took apart in [Moving the crypto out of the server](/2026-07-25-password-manager-zero-knowledge/). This page is about the system as it stands now.

## How it works

Everything starts from one secret, the master password, and fans out into keys with separate jobs. Only two of the values in this tree are ever sent to the server, and neither can decrypt anything.

```mermaid caption="The key hierarchy. Accented boxes never leave the browser; cylinders are what the server stores."
flowchart TD
  pw["Master password"] -- "Argon2id, per-user salt,<br/>64 MiB, t=3, p=4" --> mk["MK"]
  mk -- "HKDF 'auth'" --> ak["AuthKey"]
  mk -- "HKDF 'enc'" --> ek["EncKey"]
  ak -- "Argon2id again" --> hash[("auth_key_hash")]
  vk["VaultKey<br/>32 random bytes"] -- "wrapped by EncKey" --> wvk[("wrapped_vault_key")]
  ek -.-> wvk
  vk -- "AES-256-GCM per entry" --> entries[("entry blobs")]
  vk -- "wraps" --> fk["FileKey per file"]
  fk -- "1 MiB chunks" --> files[("MinIO objects")]
  class pw,mk,ek,vk,fk secret
```

1. **Setup.** The browser generates a salt and derives the master key (MK) with Argon2id. HKDF splits it into `AuthKey` and `EncKey`. A random 32-byte `VaultKey` is wrapped with `EncKey`. The server receives the salt, the KDF parameters, `AuthKey` (which it hashes again with Argon2id), and the wrapped vault key.
2. **Unlock.** The browser fetches the salt and the wrapped key, derives `EncKey` again, and unwraps the vault key locally. A wrong password fails the AES-GCM tag check, so the browser finds out without the server ever getting involved. The vault key stays in memory and locks after 15 minutes of inactivity.
3. **Save an entry.** The browser generates the entry's UUID, encrypts the entry under the vault key with that UUID in the associated data, and uploads the ciphertext. The server stores it without being able to read it.
4. **Store a file.** Each file gets its own random `FileKey`, wrapped by the vault key. The file is encrypted in 1 MiB chunks and stored in MinIO, up to 100 MB of ciphertext.
5. **Rotate the master password.** The browser unwraps the vault key with the old password and wraps it again with the new one. It sends the new material together with the old `AuthKey` as proof. No entry or file is re-encrypted.

```mermaid caption="Unlocking. The server hands over material that is useless without the master password; the decision that the password is right is made by the GCM tag in the browser."
sequenceDiagram
  participant B as Browser
  participant D as Django
  B->>D: GET /api/master-key/params/
  D-->>B: kdf_salt, kdf_params, wrapped_vault_key
  Note over B: MK = Argon2id(password, salt)<br/>EncKey = HKDF(MK, "enc")
  Note over B: VaultKey = AES-GCM open(EncKey, wrapped_vault_key)<br/>wrong password: tag check fails here
  B->>D: ciphertext requests from now on
```

## Design decisions

### Derive keys in the browser

The server must never hold anything that decrypts a vault, so the password has to become keys before it leaves the user's device. All derivation, wrapping and AEAD code lives in one frontend module, `crypto.ts`, so there is one file to audit.

<Tradeoffs>
  <div slot="considered">

  Deriving on the server with PBKDF2, as the first version did. Even without storing the result, the server would see the master password on every unlock.

  </div>
  <div slot="cost">

  Argon2id at 64 MiB runs on the user's hardware, which is slow on low-end phones. WebCrypto has no memory-hard KDF, so it comes from `hash-wasm`, a WebAssembly dependency in the most sensitive code path.

  </div>
</Tradeoffs>

### Split one master key into two with HKDF

The server needs something to check that the user knows the master password. The browser needs something to decrypt with. HKDF with different `info` labels turns one MK into both, and because HKDF is one-way, holding `AuthKey` reveals nothing about `EncKey`.

<Tradeoffs>
  <div slot="considered">

  Sending a hash of the password as the login proof. It is simpler, but it has to be derived independently from the encryption key, and every extra derivation is another place to get the separation wrong.

  </div>
  <div slot="cost">

  The server does receive one derived key in plaintext, on setup, verification and rotation. It is stored only as an Argon2id hash, and on its own it cannot unwrap anything.

  </div>
</Tradeoffs>

### Wrap a random vault key instead of encrypting under the password

Entries are encrypted with a random `VaultKey`, never with a key derived from the password. The password only protects 32 bytes: the wrapped vault key.

<Tradeoffs>
  <div slot="considered">

  Encrypting every entry directly under `EncKey`. That removes a layer, but then changing the password means re-encrypting every entry and every file.

  </div>
  <div slot="cost">

  The vault key never changes. Rotating the password does not help against a vault key that has already leaked, for example from a compromised browser session.

  </div>
</Tradeoffs>

### Unlock locally, not through the server

The server returns the wrapped key to any authenticated session and never decides whether the password is right. The AES-GCM tag check in the browser does. The server never learns whether an attempt succeeded, and no endpoint becomes a password oracle.

<Tradeoffs>
  <div slot="considered">

  An endpoint that checks `AuthKey` before releasing the wrapped key. It would put the per-user lockout in front of every unlock.

  </div>
  <div slot="cost">

  The lockout protects the endpoints that take an `AuthKey`: rotation, deleting vaults and explicit verification. It does not protect unlocking. Someone who steals a logged-in session can download the wrapped key and guess passwords offline, slowed down only by Argon2id.

  </div>
</Tradeoffs>

### Bind every ciphertext to its row

AES-GCM rejects altered ciphertext, but on its own it cannot stop someone with write access to the database from moving a valid blob to another row. The associated data is `user_id|entry_id|crypto_version`, so a blob moved to another row, reassigned to another user or downgraded to an older format fails to decrypt.

<Tradeoffs>
  <div slot="considered">

  GCM without associated data. Every blob still authenticates, but it can be swapped between rows.

  </div>
  <div slot="cost">

  The identifier has to exist before encryption, so the browser generates a UUID (`client_id`, unique in the database). Changing the format requires a version bump, because the version is part of every AAD.

  </div>
</Tradeoffs>

### Encrypt files in chunks

Files are read and encrypted 1 MiB at a time. Each chunk's AAD carries its counter and a final-chunk flag, which catches reordered, missing and truncated chunks.

<Tradeoffs>
  <div slot="considered">

  A single AES-GCM call over the whole file. It is simpler, but the browser has to hold the entire file in memory, and nothing can be decrypted until the whole download arrives.

  </div>
  <div slot="cost">

  A custom container format (magic bytes, version, base nonce) that I have to maintain, plus 16 bytes of tag per chunk.

  </div>
</Tradeoffs>

### Two rate limits, and the inner one fails closed

nginx limits login and registration to 5 requests per minute per IP. Behind it, every endpoint that takes an `AuthKey` goes through a per-user lockout in Redis: four free attempts, then 30 seconds doubling up to an hour. If Redis is unreachable, verification is refused instead of skipped.

<Tradeoffs>
  <div slot="considered">

  Failing open when the cache is down, so a Redis outage does not block users.

  </div>
  <div slot="cost">

  While Redis is down, nobody can rotate their password or delete a vault. I accept that outage over a window in which the lockout silently stops working.

  </div>
</Tradeoffs>

## What it doesn't protect

- **The JavaScript is served by the server.** A malicious deployment could ship a build that captures the master password as it is typed. In a web app, zero-knowledge is a property of the client that gets delivered, not of the protocol. A strict CSP narrows the risk but does not remove it.
- **Metadata is in plaintext.** The number of entries, timestamps, file sizes and vault membership are all visible to the operator. Search happens in the browser after decryption, because the server has nothing it could search.
- **There is no recovery.** If the master password is forgotten, the vault key stays wrapped. That is the same property seen from the user's side.

The full threat model and the status of every control are in [`AUDITORIA-SEGURIDAD.md`](https://github.com/guillesanper/django-password-manager/blob/main/AUDITORIA-SEGURIDAD.md).
